# Helpdesk AI assistant

Сервіс обробляє звернення в підтримку: приймає вебхук хелпдеску, знаходить статті в базі знань, генерує через LLM чернетку відповіді, показує її оператору, а після підтвердження надсилає відповідь клієнту через API хелпдеску.

Стек: Python 3.12, FastAPI, PostgreSQL 16, asyncpg, httpx. Запуск через `docker compose`.

## Запуск

```bash
docker compose up --build
```

Без API-ключа все працює в режимі заглушки (див. нижче). З ключем:

```bash
ANTHROPIC_API_KEY=sk-ant-... docker compose up --build
```

| Що | Адреса |
|---|---|
| Інтерфейс оператора | http://localhost:8000 |
| Вебхук | `POST http://localhost:8000/webhooks/helpdesk` |
| Мок хелпдеску (статистика) | http://localhost:9000/stats |

Надіслати одне звернення вручну:

```bash
curl -X POST localhost:8000/webhooks/helpdesk -H 'content-type: application/json' -d '{
  "event_id": "evt_1", "ticket_id": "T-1", "customer_email": "user@example.com",
  "message": "Не можу експортувати звіт у PDF",
  "reply_url": "http://helpdesk:9000/tickets/T-1/replies"}'
```

Через 5–30 с чернетка з'явиться в інтерфейсі. Після «Підтвердити й надіслати» відповідь піде на `reply_url`.

Навантажувальний тест (піки з умови: 500 звернень за 10 хвилин, з повторними доставками):

```bash
docker compose exec api python scripts/load_test.py --count 500 --duration 600
docker compose exec api python scripts/approve_all.py http://api:8000   # оператор підтверджує все
curl localhost:9000/stats                                                # duplicate_replies має бути 0
```

## Архітектура

```
helpdesk ──POST──▶ api (FastAPI) ──▶ PostgreSQL ◀── worker ──▶ LLM
                      ▲  UI оператора     (events, tickets,       └──▶ reply_url (helpdesk)
                      └──────────────────  articles, llm_calls)
```

- **api** — вебхук, інтерфейс оператора, сторінки бази знань.
- **worker** — два конвеєри: генерація чернеток та відправка відповідей. Можна запускати кілька копій.
- **db** — єдине джерело правди й одночасно черга задач.
- **helpdesk** — мок, який навмисно ламається (500, втрачені відповіді).

Статуси звернення: `queued → generating → draft_ready → approved → sending → sent`. Бокові виходи: `rejected`, `failed` (LLM не відповів), `send_failed` (хелпдеск не відповів). Для обох помилок у інтерфейсі є кнопка «Повторити».

## Як виконано вимоги

**Відповідь вебхука швидше за 2 с.** Вебхук лише записує подію й повертає 200, без LLM. На локальному тесті максимальна затримка була десятки мілісекунд.

**Повтори й дублікати, у тому числі одночасні.** Подія записується в `events` з `PRIMARY KEY (event_id)` та `ON CONFLICT DO NOTHING` в одній транзакції з створенням звернення. Дві одночасні доставки одного `event_id` дають одне звернення, друга відповідає `{"status": "duplicate"}` з кодом 200. Другу подію до того ж `ticket_id` ігноруємо: конвеєр не перезапускається.

**Піки до 500 звернень за 10 хвилин, нічого не втратити.** Звернення спершу зберігається в Postgres, і лише потім іде відповідь 200. Генерація чекає в черзі в БД, а не в пам'яті, тому перезапуск сервісу нічого не губить. Воркер бере задачі через `FOR UPDATE SKIP LOCKED`, а якщо процес впав посеред роботи, задачі з простроченим `locked_until` повертаються в чергу.

**LLM: 5–30 с на виклик, 60 запитів на хвилину на весь сервіс.** Ліміт зберігається в таблиці `llm_calls` (ковзне вікно 60 с) і перевіряється під `pg_advisory_xact_lock`, тому він діє для будь-якої кількості воркерів і не скидається при перезапуску. Для 500 звернень за 10 хвилин (≈50 за хвилину) цього вистачає. Одночасно виконується до 40 викликів (`GEN_CONCURRENCY`), щоб затримка 30 с не обмежувала пропускну здатність. Помилки 429/5xx/мережі повторюються з експоненційною паузою до 5 разів, після чого звернення отримує статус `failed`.

**Режим без API-ключа.** Запит до провайдера все одно відправляється (його відповідь ігнорується), а чернетка береться статична, зі статей бази знань, після затримки 5–30 с.

**Хелпдеск іноді повертає 5xx або не відповідає вчасно, клієнт не має отримати відповідь двічі.** Відправка йде з заголовком `Idempotency-Key: <ticket_id>` та тілом з `ticket_id`. Таймаут 10 с, повтори з паузою до 8 разів. Статус `sent` ставиться тільки після 200/201/409. Мок хелпдеску навмисно зберігає відповідь і мовчить довше за таймаут (випадок «відповідь загубилась»), а `/stats` рахує `duplicate_replies`.

**Двічі натиснута кнопка підтвердження.** Оновлення статусу має умову `WHERE status='draft_ready'`, тож повторний клік нічого не робить.

**База знань.** 7 коротких статей про вигаданий продукт «Lumio Reports» (згенеровані ШІ), лежать у таблиці `articles`. Пошук: повнотекстовий `to_tsvector('simple')` із зіставленням за префіксами слів (6 символів), бо українського стемера в Postgres немає. Чернетка містить посилання на знайдені статті, у інтерфейсі вони клікабельні. Якщо нічого не знайдено, чернетка каже, що звернення передається колезі.

## Перевірено

Запуск на локальному PostgreSQL 16 (не в docker, у моєму середовищі демон Docker був вимкнений), мок хелпдеску з 30% відмов і 10% втрачених відповідей:

- 59 доставок (40 унікальних подій, решта дублі, надіслані одночасно) створили рівно 40 звернень, максимальна затримка відповіді вебхука 25 мс.
- Усі 40 відповідей дійшли до хелпдеску рівно по одній: `duplicate_replies: 0`, попри 24 штучні помилки 500 і 3 втрачені відповіді.
- 130 звернень за 3 секунди: у будь-якому вікні 60 с було не більше 60 викликів LLM.

Не перевірялося: `docker compose up` (Dockerfile і compose написані, але не запускалися), повний прогін на 500 звернень за 600 с, реальний виклик Anthropic API з ключем, падіння воркера посеред роботи (логіка відновлення є, але не тестувалася).

## Припущення та обмеження

- Реальний хелпдеск має підтримувати `Idempotency-Key` або дедуплікувати за `ticket_id`. Інакше при загубленій відповіді неможливо гарантувати «рівно один раз» без читального API, тому гарантія «щонайменше раз + ідемпотентність».
- Вебхук не перевіряє підпис хелпдеску, а в інтерфейсі оператора немає автентифікації. Для продакшну потрібні обидва. `ALLOWED_REPLY_HOSTS` обмежує, куди воркер може надсилати відповіді (захист від SSRF).
- Одне звернення — один `ticket_id`: повторні повідомлення клієнта в тому ж звернення не обробляються.
- Інтерфейс базовий і не оновлюється сам: оновіть сторінку, щоб побачити нові чернетки.

## Змінні середовища

`ANTHROPIC_API_KEY`, `LLM_MODEL` (`claude-haiku-5-5`), `LLM_RPM` (60), `GEN_CONCURRENCY` (40), `SEND_CONCURRENCY` (20), `MAX_GEN_ATTEMPTS` (5), `MAX_SEND_ATTEMPTS` (8), `REPLY_TIMEOUT` (10), `ALLOWED_REPLY_HOSTS`, `HELPDESK_FAIL_RATE`, `HELPDESK_SLOW_RATE` (мок).
